How every feature in Lunary connects

The interesting architectural decision in Lunary is not any single feature. It is that the chart, transits, tarot, journal, grimoire, and Astral Guide are designed to reinforce each other instead of existing as isolated tools.

3 min readarchitectureproductsystemsastrology

The most interesting architectural decisions in a product are usually not about individual features. They are about how features relate to each other.

There is a meaningful difference between an app that has five features and an app where five features form a system.

In the first kind of product, each feature is a dead end. In the second, using one part of the product makes the others more useful.

Lunary was built as the second kind.

The core decision

The foundational decision was simple: treat the user's chart as persistent infrastructure, not as one-time input.

A lot of astrology products ask for birth data, generate a chart, then effectively discard it. The chart is a setup step.

In Lunary, the chart is the spine.

That one decision changes what the rest of the product can be.

What the chart powers

Once the chart is treated as a durable foundation, other features stop being separate tools.

The chart powers:

  • personal transits
  • house-based interpretation
  • compatibility and synastry
  • personalised tarot logic
  • Astral Guide context
  • journalling prompts
  • long-term pattern detection

That means the user's core data keeps compounding in value instead of being consumed once and forgotten.

The feature graph

The connections are where the product starts behaving like a system.

The birth chart feeds the transit layer.

The transit layer shapes what feels active now.

That current context informs tarot interpretation and daily guidance.

Tarot and reflection feed the journal.

The journal captures mood tags, cards, moon phases, and recurring themes.

The Astral Guide can then use the chart, current transits, tarot history, and journal patterns together.

The grimoire sits underneath all of it as the interpretive layer and retrieval source.

None of these features is strongest in isolation. Their value comes from the fact that they are aware of each other.

Why this is harder to build

Interdependent features are more expensive than isolated ones.

Each connection adds code, state, schemas, edge cases, and design complexity. A change in one part of the system can ripple through several others. You cannot build a feature and forget it. You have to think about what it unlocks, what it depends on, and what it might break.

That is real overhead.

It is also what makes the product feel like a product rather than a bundle.

Why it is worth it

When the features connect properly, the value compounds with use.

A journal is more useful when it knows the moon phase and the cards that appeared. Tarot is more useful when it understands the chart. The guide is more useful when it knows the chart, the current sky, and the user's recent patterns. Transits are more useful when they connect back to reflection instead of sitting in a calendar alone.

The result is a different user experience.

Instead of opening one feature, using it, and leaving, people move through a chain of related surfaces that all deepen the same underlying model of themselves.

The system I wanted

I did not want Lunary to feel like:

  • chart screen
  • tarot screen
  • journal screen
  • AI chat screen

all living beside each other with no memory.

I wanted it to feel like one continuous system where each feature gives the next one more context.

That is the architectural idea underneath the whole app.

The individual features matter. The graph matters more.
